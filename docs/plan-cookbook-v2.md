# แผนพัฒนา: จากชุดสูตร → คู่มือทำอาหารที่ทำตามได้จริง (ทำกินและทำขาย)

สถานะ: **เฟส A และ B พัฒนาในเครื่องแล้ว รอเผยแพร่และตรวจบนเว็บจริง** (อัปเดต 7 พ.ย. 2569)
อ้างอิงจากการวิเคราะห์ข้อ 1–8 ที่ทำไปแล้ว (โค้ดแยกไฟล์, ความปลอดภัย, ข้อมูลหาย, PWA, ประสิทธิภาพ, UX, จัดระเบียบ repo, สารก่อภูมิแพ้/วันที่ราคา)

## 1. ทิศทางและหลักการ

- **ผู้ใช้สองกลุ่มใช้เล่มเดียวกัน:** คนทำกินเองและคนทำขาย ส่วนทำขาย (ต้นทุน ราคา ใบเสนอราคา) เปิดไว้ให้ทุกคนเห็นเป็นความรู้ ไม่ซ่อน แต่ต้องอธิบายให้เข้าใจได้โดยไม่ต้องมีพื้นฐานธุรกิจ
- **เป้าหมายหลักคือ "คู่มือทำตามได้จริง"** ส่วน SOP สำหรับทำขายเป็นชั้นเสริม (เฟส D) ที่ทำเมื่อพร้อมมีข้อมูลจริง
- **ตัวเลขเรื่องความปลอดภัยอาหารต้องมาจากการทดลองและวัดจริงของเจ้าของสูตร** (อุณหภูมิแกนกลาง เวลาพักอาหาร อายุการเก็บ) ห้ามเดาหรือแต่งขึ้นเอง ข้อมูลกฎหมาย/การขึ้นทะเบียนให้ตรวจกับหน่วยงานในพื้นที่ก่อนเขียนเป็นข้อเท็จจริง
- ทุกงานต้อง: เทสต์ผ่าน (`npm test`), ตรวจบนเว็บจริงหลัง deploy, ไม่ทำให้ข้อมูลที่ผู้ใช้บันทึกไว้หาย (ฟอร์แมตไฟล์สำรองคงเดิม)

## 2. ลำดับเฟส (ทำจากเล็กและเห็นผลเร็วไปใหญ่)

| เฟส | เรื่อง | ขนาด | ต้องการข้อมูลจากเจ้าของ |
|---|---|---|---|
| A | อธิบายศัพท์ส่วนทำขาย | เล็ก | ทำในเครื่องแล้ว รอตรวจหลังเผยแพร่ |
| B | ปรับจำนวนจาน + แยกเวลาเตรียม/ปรุง | กลาง | ทำในเครื่องแล้ว ใช้เวลาโดยประมาณ 20 เมนูแรก รอตรวจหลังเผยแพร่ |
| C | เนื้อหาสูตรเพิ่ม (ทดแทน ความเผ็ด แก้ปัญหา ฯลฯ) | ใหญ่ | ใช่ ต้องตรวจทุกสูตร |
| D | ชั้น SOP ความปลอดภัยอาหาร + แบบฟอร์ม | ใหญ่ | ใช่ ค่าที่วัดจริง |
| E | ความถูกต้องของข้อมูลและความทนทานของระบบ | กลาง | ใช่ ตรวจสารก่อภูมิแพ้/โภชนาการ |
| F | ขยายเนื้อหา (หมวดใหม่ ภาพขั้นตอน ภาษา) | ใหญ่ | ใช่ รายชื่อเมนู สูตร ภาพ |

เฟส A และ B ไม่ขึ้นต่อกัน เริ่มพร้อมกันได้ เฟส C ควรทำหลัง B (ใช้โครงข้อมูลใหม่ร่วมกัน) เฟส D ควรทำหลัง C เฟส E แทรกได้ทุกเมื่อ ส่วนข้อ E3 ควรทำก่อนเผยแพร่เป็นคู่มือจริง

## เฟส A — อธิบายส่วนทำขายให้ทุกคนเข้าใจ

เป้าหมาย: คนทำกินเองเปิดดูแล้วไม่งง และได้ความรู้เรื่องต้นทุนไปด้วย

**สถานะ:** A1–A4 ทำในเครื่องแล้ว เพิ่มคำอธิบายและตัวอย่างใต้ช่องตั้งค่า ป้ายเครื่องมือทำขาย และบทก่อนเริ่มขาย การตรวจบนเว็บจริงยังรอหลังเผยแพร่

- **A1 อธิบายศัพท์ในหน้าตั้งค่าร้านและเครื่องคำนวณ:** "ส่วนต่างเป้าหมาย", "ค่าธรรมเนียมจากยอดขาย", "ค่าแรงต่อกล่อง", "ค่าน้ำไฟ", "VAT ของค่าธรรมเนียม" พร้อมตัวอย่างตัวเลขสั้น ๆ ใต้ช่องกรอก
- **A2 บอกชัดว่าข้ามได้:** ค่าแรง/ค่าน้ำไฟ/ค่าธรรมเนียมเริ่มต้นเป็น 0 ใช้ต้นทุนวัตถุดิบอย่างเดียวได้เลย (เพิ่มประโยคบอกในหน้า)
- **A3 ตั้งชื่อและจัดกลุ่ม:** ป้ายบอกว่า "ใบเสนอราคา/สติกเกอร์ฝากล่อง" เป็นเครื่องมือเสริมสำหรับคนทำขาย
- **A4 บทสั้น "ก่อนเริ่มขาย"** (แทนข้อความท้ายหน้าที่สั้นเกินไป): วิธีคิดต้นทุนจริง (ค่าแรง ค่าน้ำไฟ ของเสีย) และเตือนให้ตรวจข้อกำหนดท้องถิ่น โดยไม่ระบุรายละเอียดทางกฎหมายเอง

ไฟล์ที่เกี่ยวข้อง: `website/index.html`, `website/js/recipe-detail.js` (เครื่องคำนวณ), `website/style.css`
เกณฑ์ผ่าน: ทุกช่องตั้งค่ามีคำอธิบาย อ่านแล้วเข้าใจโดยไม่ต้องถามใคร เทสต์ยังผ่าน

## เฟส B — ปรับจำนวนจาน และแยกเวลา

เป้าหมาย: คนทำกินในบ้านใช้ได้ทันที

**สถานะ:** B1–B4 ทำในเครื่องแล้ว หน้าสูตรและรายการซื้อใช้จาน/กล่อง ปรับคำแนะนำเมื่อทำครั้งละมาก และเพิ่ม `prepTime` / `cookTime` หน่วยนาทีสำหรับ 20 เมนูแรก พร้อมเรียงตามเวลารวมและทดสอบ เมนูอื่นยังใช้ `time` เดิม รวมเวลาแช่ที่ระบุในข้อความเมื่อเรียงลำดับ

**ที่มาของเวลา:** ผู้ใช้เห็นชอบให้ใช้ค่าประมาณจากขั้นตอนสูตรเพื่อช่วยวางแผน ไม่ใช่ค่าที่จับเวลาจริง สมมติว่ามีข้าวสวยและวัตถุดิบที่ระบุว่าสุกแล้ว เวลาจริงขึ้นกับคนทำและอุปกรณ์ ควรปรับเมื่อมีผลทดลอง การตรวจบนเว็บจริงยังรอหลังเผยแพร่

- **B1 ปรับตามจำนวนคน/จาน:** ตอนนี้หน่วยเป็น "กล่อง" ใช้คำว่า "จาน/กล่อง" ให้สอดคล้อง และให้เลือกจำนวนได้ในหน้าสูตร (ระบบคูณจำนวนกล่องมีอยู่แล้ว ใช้ต่อได้)
- **B2 ข้อควรระวังเมื่อทำเยอะ:** ข้อความว่าซอส น้ำตาล น้ำมัน ไม่ควรคูณเป็นเส้นตรงเสมอ ให้ชิมปรับ (เนื้อหานี้ผมร่างให้ เจ้าของตรวจ)
- **B3 แยกเวลา:** ฟิลด์ใหม่ `prepTime` และ `cookTime` แทน `time` เดิม (เก็บ `time` เดิมไว้เพื่อความเข้ากันได้กับการเรียงลำดับ) แสดงบนการ์ดและหน้าสูตร
- **B4 อัปเดตการเรียงลำดับ** ให้ใช้เวลารวม

ข้อมูลที่ควรเก็บเพิ่มเติม: เวลาเตรียมและปรุงจริงจากการทดลอง โดยเฉพาะผู้ที่ยังไม่เคยทำสูตร เพื่อปรับค่าประมาณให้แม่นยำขึ้น
เกณฑ์ผ่าน: ทุก 20 เมนูมีสองค่า ตัวเลขรวมของการเรียงลำดับถูกต้อง มีเทสต์ครอบ

## เฟส C — เนื้อหาสูตรให้ทำตามได้จริง

เพิ่มฟิลด์ต่อสูตร (ตัวเลือก ไม่บังคับ — สูตรที่ยังไม่มีข้อมูลแสดงเป็นว่าง ไม่ขึ้นข้อความแปลก):

| ฟิลด์ | ตัวอย่างเนื้อหา |
|---|---|
| `equipment` | กระทะแบน 28–30 ซม. ตะหลิว เขียง |
| `substitutions` | กะเพรา → โหระพา, ไก่ ↔ หมู, ไม่กินหอยนางรม → ซีอิ๊วขาวเพิ่มเล็กน้อย |
| `spice` | ลดพริกอย่างไรสำหรับเด็ก/ไม่ทนเผ็ด |
| `troubleshooting` | เค็มไป ซอสแห้งไป ไข่ไม่สุก ใบกะเพราดำ |
| `buying` | วิธีเลือกพริกแกง/ซอส ปริมาณที่ซื้อ |
| `storage` | เก็บในตู้เย็นกี่วัน อุ่นซ้ำอย่างไร (ต้องตั้งจากการทดลอง) |

- **C1 ออกแบบโครงข้อมูลและแสดงผล** ในหน้าสูตร (พับ/ขยายได้ ไม่ให้หน้ายาวเกิน)
- **C2 ร่างเนื้อหา 20 เมนู** ให้เจ้าของตรวจทีละเมนู (ผมร่าง คุณยืนยันว่าทำได้จริง)
- **C3 ปรับส่วนผสมและขั้นตอนให้ชัด** เช่น ระบุว่าส่วนผสมเป็นน้ำหนักก่อนหรือหลังตัดแต่ง
- **การตัดสินใจที่ต้องทำก่อน:** ข้อมูลสูตรถูกสร้างจาก `source/prepare.py` (ตารางต้นทาง) แล้วเขียนเป็น `website/data.js` จะแก้ที่ต้นทางต่อ หรือเลิกใช้สคริปต์แล้วแก้ `data.js` ตรงเป็นแหล่งจริง (แนะนำอย่างหลัง เพราะง่ายกว่าและ diff ใน git อ่านได้)

เกณฑ์ผ่าน: ทุกเมนูที่เจ้าของยืนยันแล้วมีเนื้อหาครบอย่างน้อย 4 ใน 6 ฟิลด์ ไม่มีฟิลด์ไหนมีข้อมูลที่ไม่ผ่านการตรวจ

## เฟส D — ชั้น SOP สำหรับทำขาย (ทำเมื่อพร้อมมีข้อมูลจริง)

เป้าหมาย: ให้คนอื่นผลิตซ้ำได้เหมือนกันและควบคุมความปลอดภัยอาหารได้

- **D1 ฟิลด์ต่อสูตร:** น้ำหนักสุทธิต่อกล่อง, เกณฑ์ตรวจรับ (สี รส ความสุก), อุณหภูมิแกนกลางที่ต้องถึง, เวลาสูงสุดจากปรุงถึงลูกค้า, การลดอุณหภูมิก่อนปิดฝา, อายุการเก็บและวิธีเก็บ, วิธีอุ่นซ้ำ, ขนาดชุดผลิตสูงสุด และเวลาที่เปลี่ยนเมื่อผลิตเป็นชุด
- **D2 หน้า SOP ระดับร้าน:** สุขลักษณะส่วนบุคคล, การรับและเก็บวัตถุดิบ, การแยกของดิบ/สุก, การทำความสะอาด, การจัดส่ง
- **D3 แบบฟอร์มพิมพ์ได้:** บันทึกการผลิตรายวัน, บันทึกอุณหภูมิ, ใบตรวจรับวัตถุดิบ
- **D4 การควบคุมเอกสาร:** เลขเวอร์ชัน วันที่อนุมัติ ผู้รับผิดชอบ ประวัติการแก้ไข แสดงในหัวเอกสารและบนใบพิมพ์
- **D5 ปรับข้อความในเว็บ:** แยกสูตรที่ "ทดลองและรับรองแล้ว" กับ "ยังเป็นตัวอย่าง" ไม่ใช้คำว่า SOP กับสูตรที่ยังไม่ผ่านการรับรอง

ข้อมูลที่ต้องการจากเจ้าของ: ค่าที่วัดจริงจากการผลิต ผมไม่เดาตัวเลขเหล่านี้ ข้อกำหนดของ อย./เทศบาลสำหรับการขายข้าวกล่องต้องตรวจกับหน่วยงานก่อนเขียนลงเว็บ
เกณฑ์ผ่าน: สูตรต้นแบบ 1–2 เมนูผ่านครบทุกฟิลด์ด้วยค่าที่วัดจริง คนที่ไม่เคยทำสูตรนี้ทำตามแล้วได้ผลเท่ากัน (ทดสอบกับผู้ใช้จริงอย่างน้อย 1 คน) ก่อนขยายเป็น 20 เมนู

## เฟส E — ความถูกต้องของข้อมูลและความทนทานของระบบ

- **E1 ตัวกันหน้าพังหลัง deploy:** ตรวจว่าองค์ประกอบสำคัญหายไปหรือไม่ (เคยเจอ HTML ใหม่คู่ JS เก่า/ใหม่ไม่พร้อมกันหลัง deploy) แล้วโหลดหน้าใหม่หนึ่งครั้ง มีตัวกันวนซ้ำ
- **E2 ตรวจสารก่อภูมิแพ้ทั้ง 20 เมนู:** กฎปัจจุบันจับคำจากชื่อส่วนผสม ผลบางเมนูน่าสงสัย (เช่น เมนู 19 และ 20 ขึ้น "นม") ให้เจ้าของสูตรตรวจกับส่วนผสมและฉลากจริง แล้วเปลี่ยนจากการจับคำเป็นฟิลด์ระบุเองรายสูตร
- **E3 ตรวจค่าโภชนาการ:** ตอนนี้เป็นตัวเลขประมาณ ถ้าจะอ้างเป็นคู่มือควรคำนวณจากฐานข้อมูลอาหารที่น่าเชื่อถือ หรือบอกที่มาให้ชัด
- **E4 วันที่ราคา:** ยืนยันแล้วว่า "ตุลาคม 2569" ตรง ให้ตั้งรอบทบทวนราคาและอัปเดต `PRICE_DATA_DATE` ทุกครั้งที่ปรับราคา
- **E5 ตรวจสอบ GitHub Actions** ว่าเทสต์ผ่านบน GitHub จริง (ยังไม่เคยดูผล)
- **E6 วัด Lighthouse และทดสอบบนมือถือจริง** รวมถึงทดสอบออฟไลน์และติดตั้งเป็นแอปบน Android (ยังไม่ได้ทำ)

## เฟส F — ขยายเนื้อหา

- **F1 เมนูหมวดใหม่** (ต้ม ยำ ขนม): มีสูตรและภาพประกอบ AI ในเว็บไซต์แล้ว โดยสูตร ต้นทุน และภาพยังต้องให้ผู้มีความรู้ตรวจหรือทดลองก่อนถือเป็นสูตรที่รับรองแล้ว
- **F2 ภาพขั้นตอน:** ภาพจริงในขั้นตอนสำคัญ เพื่อให้มือใหม่เห็นว่า "สุกทั่ว" หน้าตาเป็นอย่างไร ภาพที่สร้างด้วย AI ต้องระบุชัดเมื่อใช้ประกอบ
- **F3 สองภาษา** (ไทย/อังกฤษ): ต้องแยกข้อความออกจากโค้ดก่อน ควรทำเมื่อเนื้อหานิ่งแล้ว
- **F4 แบ่งปันสูตร:** ลิงก์แชร์มีอยู่แล้ว (พารามิเตอร์ใน URL) ตรวจว่าใช้กับหน้าสูตรใหม่ได้

## 3. สิ่งที่ต้องการจากเจ้าของ (ตัดสินใจ/ให้ข้อมูล)

1. ตัดสินใจ: แหล่งข้อมูลจริงของสูตรคือ `prepare.py` หรือ `data.js` โดยตรง
2. เมื่อมีโอกาส ทดลองจับเวลาเตรียมและปรุง 20 เมนูเพื่อปรับค่าประมาณ (เฟส B)
3. ตรวจร่างเนื้อหาสูตรทีละเมนู: ของทดแทน การปรับความเผ็ด การแก้ปัญหา การเก็บ (เฟส C)
4. เมนูต้นแบบ 1–2 เมนูที่มีค่าวัดจริง และคนทดสอบทำตามหนึ่งคน (เฟส D)
5. ผลตรวจสารก่อภูมิแพ้และโภชนาการ (เฟส E)
6. ข้อมูลข้อกำหนดท้องถิ่นสำหรับการขาย (ตรวจเอง ผมไม่เขียนเป็นข้อเท็จจริง)

## 4. ความเสี่ยงและข้อควรระวัง

- **ข้อมูลที่ผู้ใช้บันทึกไว้:** ฟอร์แมตไฟล์สำรอง (`thai-kitchen-backup` v1) และ `validBackup` ต้องไม่พัง เมื่อเพิ่มฟิลด์ในสูตร (ข้อมูลสูตรไม่อยู่ในไฟล์สำรอง จึงปลอดภัย) แต่ถ้าเปลี่ยนโครงเก็บของผู้ใช้ ต้องมี migration และเทสต์
- **service worker/แคช:** เวอร์ชันแคชถูกประทับอัตโนมัติจาก hash ตอน deploy จึงไม่ต้องแก้มือ แต่ถ้าเพิ่มไฟล์ JS/ภาพใหม่ต้องเพิ่มในรายการแคชใน `sw.js`
- **ข้อความเรื่องความปลอดภัย:** ห้ามใส่ตัวเลขที่ไม่ได้มาจากการทดลอง ถ้าสูตรใดยังไม่ผ่านการรับรอง ให้ขึ้นข้อความบอกชัด
- **ความยาวหน้าสูตร:** เนื้อหาเพิ่ม 6–10 หัวข้อต่อสูตร ถ้าไม่จัดพับ/แท็บ หน้าจะยาวจนใช้ยากบนมือถือขณะทำอาหาร

## 5. ข้อเสนอลำดับเริ่มงานเมื่อพร้อม

1. ตัดสินใจเรื่องแหล่งข้อมูล (หัวข้อ 3 ข้อ 1)
2. เฟส A (งานเล็ก เห็นผลทันที) และ E1, E5 พร้อมกัน
3. เฟส B
4. เฟส C เริ่มจาก 3 เมนูก่อน ตรวจกับเจ้าของ แล้วค่อยขยาย
5. เฟส D เฉพาะเมนูต้นแบบ แล้วทดสอบกับผู้ใช้จริง
6. เฟส E2–E3 ก่อนประกาศใช้เป็นคู่มือ
